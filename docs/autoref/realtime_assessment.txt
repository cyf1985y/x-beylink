即時處理評估（本機補測，未修改產品程式碼）

結論：目前辨識核心在這台桌機具備即時運作的算力條件。20～30 fps 有較多餘裕；60 fps 仍需瀏覽器完整流程與真機實測。速度可行不等於判定可靠。

主機：Intel Core i5-9400 2.90 GHz、6 logical cores、24 GB RAM、Node 24.14.0。
輸入：原影片 00:45–01:15、720×720 / 60 fps，縮至 480×480，以原版 VisionProcessor + RefereeEngine 運算。
總共 1,800 格，排除前 120 格暖機後統計。這次不寫逐格 JSON。

辨識＋規則耗時：
- 平均：12.06 ms / 格
- 中位數：11.96 ms / 格
- p95：13.49 ms / 格（95% 的格在此時間內完成）
- p99：15.22 ms / 格
- 最慢：47.21 ms / 格
- 超過 60 fps 的 16.67 ms 預算：約 0.60%
- 超過 30 fps 的 33.33 ms 預算：約 0.06%
- 離線解碼＋運算總時間：23.49 秒，處理 30 秒影片

每格預算：20 fps = 50 ms；30 fps = 33.33 ms；60 fps = 16.67 ms。

原先完整影片測試是另一組數據：32,201 格平均影像核心 13.88 ms，核心累計 446.94 秒（約 7 分 27 秒）。整個任務還包含下載、取得程式碼、建測試工具、校正、人工查看、不同設定重跑、產生逐格紀錄與疊圖影片。這些不能當成直播時每格的延遲。

原版已有 Web Worker，一次只處理一格、忙碌時丟棄新格，因此不會無限堆積影格；但丟格仍可能影響短事件與停轉判定。每格辨識不需要呼叫 Claude 或其他雲端模型。

運算時間與裁決時間也不同：規則本來就要求停轉連續確認 0.15 秒；部分進區情況會等待 1.5 秒消失確認或 3 秒停留確認。這是規則等待時間，另需加上取格、運算與顯示延遲。

尚未測量：手機／iPhone Safari、瀏覽器 canvas 取格、Worker 往返、UI、錄影、相機到裁決的端到端延遲、長時間熱降頻。不能把離線吞吐量直接當成相機實際 fps。

建議驗收：固定俯拍原始影片，正確空盤校正；先以 30 fps 測試並記錄每格處理 p95/p99、丟格率、取格到裁決延遲；同時修正假手部與未知觀測的早判，最後在目標手機連續運作 10～15 分鐘並比對人工逐局標註。降低幀率會改變每格角度訊號，必須重新驗證準確性，不能只降 fps 就宣稱問題解決。
