# 交接單：天梯 M1（1v1 排位）

> 這份文件是 M1 實作時的規格來源。資料庫端（表、RPC、Elo 計算）已全部完成並在正式環境測試通過，
> 應用層**不得**自行計算積分，一律呼叫 `ladder_confirm_result`。

## 一、頁面

```
/ladder                    排行榜（當季）＋我的積分卡＋道館入口
/ladder/gym/[id]           道館頁：進場、在場名單、挑戰
/ladder/match/[id]         對戰頁：計分 → 回報 → 敗方確認／異議
/api/cron/ladder           呼叫 ladder_maintenance（驗 CRON_SECRET，比照 /api/cron/confirm）
```

- `/ladder/gym/[id]?t=<token>`（QR 進場）**M1 不做**，認證道館是 M2。
- cron 必須驗 `CRON_SECRET` 並加進 `vercel.json`；或併進既有 confirm cron 也可以。

## 二、UI 要點

- **進道館**：`navigator.geolocation` 一次性讀取（**不要** `watchPosition`）。座標只傳 RPC，
  拒絕定位時顯示明確訊息。
- **道館頁**：挑戰者名單（暱稱＋頭像＋段位），10 秒輪詢即可。
- **計分**：複用既有計分板元件。
- **敗方確認頁**：「對手回報 X:Y 獲勝，正確嗎？」〔確認〕〔有問題〕，
  並註明 10 分鐘未操作自動成立。
- **段位**：

  | 分數 | 段位 |
  |---|---|
  | < 1050 | 見習戰士 🌱 |
  | ≥ 1050 | 戰士 ⚔️ |
  | ≥ 1150 | 精英 🛡️ |
  | ≥ 1300 | 大師 🔥 |
  | ≥ 1450 | 王者 👑 |

  畫面以段位為主、分數小字。
- **排行榜**：當季 rating desc 只取前 20，通常組／公開組分開。
- **選手卡**：加「天梯」區塊，與獎盃牆分區。

## 三、驗收清單

1. 道館 150m 內可進場，遠處被拒且訊息清楚
2. 兩支手機同道館可互見、挑戰、計分
3. 敗方確認後雙方分數即時變動（首戰 1000 vs 1000 = ±16）
4. 勝方按確認被拒
5. 同兩人當日第 2 場減半、第 3 場不動分
6. 座標不出現在任何 log／表／URL
7. 排行榜只前 20、分組
8. 重整後能回到進行中對戰（查 `status='playing'`）
9. `npx tsc --noEmit` 與 `npm run lint` 通過

## 五、後端契約（讀自正式環境，供實作參考）

**表**：`ladder_seasons`、`ladder_ratings`、`ladder_matches`、`ladder_gym_presence`、
`gyms`／`gyms_public`（view，不含 `qr_token`）

**狀態機**：`playing` → `pending_confirm` → `confirmed`／`disputed`／`voided`

| RPC | 參數 | 規則 |
|---|---|---|
| `ladder_enter_gym` | `p_gym_id, p_player_id, p_lat, p_lng, p_token` | 有 token 走 QR 驗證；沒 token 才用 GPS 比 `radius_m`。在場效期 30 分鐘。錯誤：`no_active_season` / `gym_not_found` / `bad_token` / `location_required` / `too_far` |
| `ladder_challenge` | `p_gym_id, p_challenger, p_opponent` | 雙方都須在場未過期；任一方有進行中對戰即擋。錯誤：`self_challenge` / `challenger_not_present` / `opponent_not_present` / `match_in_progress` |
| `ladder_report_result` | `p_match_id, p_reporter, p_score_a, p_score_b` | 只有參賽者能報、分數不可相同或為負。錯誤：`not_participant` / `bad_score` / `bad_status` |
| `ladder_confirm_result` | `p_match_id, p_confirmer` | **只有敗方能確認**（`not_loser`）。Elo 全在此計算 |
| `ladder_dispute` | `p_match_id, p_player` | 同樣只有敗方 |
| `ladder_maintenance` | 無 | 回傳 `autoconfirmed` / `voided_stale`，給 cron |
| `ladder_void_match` | `p_match_id` | 管理端作廢 |

**Elo（`ladder_confirm_result` 內）**：K＝32（未滿 10 場）／16；
有效係數＝同日同對手第 1 場 ×1、第 2 場 ×0.5、第 3 場起 0；單日滿 3 場計分場後歸零。
rating 下限 900，另記 `peak_rating`。

## 六、實作備註

- `ladder_confirm_result` 的 `p_confirmer` 傳 NULL 會**跳過敗方檢查**（給 maintenance 自動成立用），
  應用層一律要帶入確認者的 player_id。
- 「通常組／公開組」以 `players.role` 區分：`child` → 通常組、`parent` → 公開組。
- 自動成立的即時性靠**頁面載入補跑** `ladder_maintenance`（沿用本專案 settle／autoBracket 的慣例），
  cron 只作為每日掃底。
